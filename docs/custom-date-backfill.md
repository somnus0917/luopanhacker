# 指定日期补采设计草案

## 结论

补采指定日期应继续通过罗盘页面完成日期选择，让页面生成合法的签名请求；不建议直接修改已捕获请求中的 `begin_date` / `end_date`，因为请求签名可能覆盖日期参数。

日历操作比“近1天”多两到三次点击，交互失败概率会增加，但数据可靠性不应依赖点击是否成功。采集器必须读取 `core_index_v3` 的实际请求日期，并且仅在开始、结束日期都等于目标日期时保存结果。这样最坏情况是本次补采明确失败，而不是把错误日期写入数据库。

## 本地原型范围

- 新增 Python 参数 `--date YYYY-MM-DD`。
- 不传 `--date` 时，现有“近1天”逻辑完全不变。
- 原型仅允许 `--module operations`。
- 为与当前日历能力保持一致，页面、API 和采集命令均只接受本月 1 日至昨天。
- 自定义日期优先通过完整日期属性定位，例如 `title="2026-07-25"`、`data-date="2026-07-25"` 或完整 `aria-label`。
- 如果组件只有日期数字，则仅在同时包含目标年月的可见面板中、且数字唯一时才点击。
- 同一天最多点击两次，以兼容“开始日期 + 结束日期”的区间选择器。
- 当前不自动跨月；通过入口日期范围限制，避免提交其他月份后才失败。
- 真实页面验证确认第一次点击填写开始日期，第二次点击同一天填写结束日期并自动刷新，不需要确认按钮。
- 自定义请求使用 `date_type=999`；选择完成后，只接受该类型业务接口返回的目标日期作为成功依据。

本地命令示例：

```bash
UV_CACHE_DIR=.uv-cache uv run python apps/collector_py/scheduler.py \
  --random-delay-seconds 0 \
  --module operations \
  --shop "华硕凡飞笔记本电脑专卖店" \
  --date 2026-07-25
```

## 为什么暂不支持渠道模块

渠道采集会滚动多个子模块，并在每个模块内再次点击“近1天”。只修改页面顶部日期会导致不同响应混用不同日期。渠道补采必须为每个日期标签组分别执行自定义日期选择，并逐条验证响应中的日期字段，完成真实页面验证前不应开放。

## 建议的上线步骤

1. 用本地有效登录会话验证罗盘真实日历 DOM、同日区间的点击次数和确认按钮。
2. 如需补采更早月份，再增加跨月导航；每次导航后重新读取可见年月，禁止按固定次数盲点。
3. 将 `--date` 和 `--shop` 透传到 Rust worker。
4. 为看板增加“补采日期 + 店铺 + 模块”请求参数，并将任务类型标记为 `backfill`。
5. 数据库存储保持按“店铺 + 业务日期”幂等覆盖，补采成功后核对四家店是否齐全。
6. 渠道模块完成独立日期选择和响应日期验证后再开放。
